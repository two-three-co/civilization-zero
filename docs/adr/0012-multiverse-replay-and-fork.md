# ADR-0012: Multiverse Runtime — 再生は再実行、分岐は「開始状態 + 介入」、台帳は完全性検査

- 状態: 採用 (2026-10-17)
- 対象: ADR-0010 の 2a-4（再生）・2a-5（fork）。実装は `crates/multiverse`
- 計測: Apple M1, release, 1,000 体 → 定常約 1,300 体, 128²

## 文脈

Toy 1 の「巻き戻し・分岐・比較」には、任意 tick の状態を復元し、そこから介入付きで分岐する基盤が要る。
カーネル（`simulation-core`）は決定論的で、台帳（`EventLog`, 2a-2）には介入と出生・死亡が tick 付きで並んでいる。

## 決定

### 1. 再生 = 再実行（イベントソーシングではない）

`replay(world, log, to)` は、スナップショットから `to` まで **step し直す**。各 tick で台帳のその tick の `Intervened` を先に適用し、
step の結果の出生・死亡イベントが台帳のそれと**完全一致**しなければ `ReplayError::Diverged { tick, expected, got }`。

理由: 出生・死亡は入力ではなく遷移の出力なので、状態を「イベントから組み立てる」必要はない。カーネルが同じ入力から同じ出力を出すことこそ契約であり、
照合に使えば、再生のたびに「台帳がこの世界のものか」「カーネルのバージョンが同じか」を検査できる（改竄・取り違え・遷移関数の変更をその tick で検出）。

### 2. `state_at(T)` は「tick T の開始状態」

T の介入を適用する**前**の状態と定義する。スナップショットは step 直後に取るので常にこの定義に合い、head に介入を適用した直後の一時状態とは区別される。
`replay` も `to` 時点の介入は適用しない。この定義により、分岐・再生・比較のどこでも「tick T」が同じ意味になる。

### 3. 分岐 = 親の開始状態 + 子の介入。台帳は過去をコピーする

`fork(from, at, interventions)`:
- `state_at(from, at)` を origin スナップショットとして持つ（子の介入を適用する前）。
- 子の台帳 = 親の台帳の `0..at` のコピー + 子の介入（tick `at`）。親の `at` における介入は**継承しない**（必要なら引数で渡す）。
- 系譜は `Branch { parent, forked_at }`。

これで各ブランチは親を参照せずに単独で再生できる（origin スナップショット + 自分の台帳）。台帳のコピーは 20,000 tick で約 6 MB。
二重適用の問題（origin に含まれる介入を再生で再度適用）は、origin を介入前の状態にすることで構造的に起きない。

### 4. スナップショットの間隔は復元時間の上限

`Multiverse::new(root, snapshot_every)`。復元コストは最大 `snapshot_every` tick 分の再実行。

| 条件 | 計測値 |
|---|---|
| root を 2,000 tick 進める（1,300 体、台帳 6,110 イベント） | 304.5 ms |
| `state_at(750)`、間隔 500（スナップショット 500 から 250 tick 再生） | **33.1 ms** |
| `state_at(950)`、間隔 100（50 tick 再生） | **6.7 ms** |
| スナップショット上の tick | 0.01 ms（clone のみ） |
| `fork`（clone + 介入 2 件） | **0.07 ms** |
| `cz replay`: バイナリスナップショット（tick 1,000）+ 台帳で 2,000 まで | 84.2 ms（11,875 tick/s）、2,684 イベント照合、直接実行とハッシュ一致 |

ブラウザ（wasm、native の約 3.8 倍遅い）で 2b-4 の目標「巻き戻し ≤ 200 ms」を満たすには、間隔 500 では最悪 250 ms 程度になるため **間隔 200〜250** を初期値にする。
メモリ: バイナリスナップショット 1 つ約 57 KB → 20,000 tick を間隔 200 で 100 個 = 5.7 MB/ブランチ（許容）。

### 5. 再現性の契約（拡張）

同一のカーネル版 + 同一の origin スナップショット + 同一の台帳 → 同一の状態列。`cz fork` は同じ介入で 2 回 fork して head のハッシュ一致を表示する（`tests/fork.rs` でも検証）。

## 却下した代替案

- **イベントソーシング（状態をイベントから再構築）**: 出生・死亡だけでは状態（位置・エネルギー）が再構築できず、全行動の記録が必要になり台帳が 1 tick あたり 1,000 件超になる。再実行の方が安く、照合で同じ保証が得られる。
- **分岐が親スナップショットを共有参照する**: メモリは節約できるが、親の変更やスナップショット削除で子が壊れる。コピーの方が単純で、サイズは問題にならない。
- **`state_at(T)` を「T の介入適用後」にする**: head と再生で定義が食い違い、origin の二重適用問題が生じる。

## 帰結

- `crates/multiverse` は `simulation-core` にのみ依存。カーネルはファイルも分岐も知らない。
- Phase 5（実験スケジューラ）は `fork` を多シード・条件格子で呼ぶだけで済む。
- 2b-1（wasm パッケージ）は `Multiverse` をそのまま包む。Worker 1 つ = `Multiverse` 1 つ（複数ブランチを持てる）か、ブランチごとに Worker かは 2b-1 で決める。
  → 2b-6 で **ブランチごとに Worker** を採用した。fork は親が `state_at(T)` のバイナリスナップショットを書き出し、子ワーカーが `WasmWorld::fromSnapshot` で原点にして介入を適用する。
  子の台帳は T から始まる（親の過去は持たない）が、`Multiverse::fork` と状態・ハッシュが bit 一致することをテストで確認済み（`cz-web/tests/native.rs`）。各ブランチが別スレッドで走るので、2 世界の同期再生でも 1 世界と同じ tick/s が出る。
