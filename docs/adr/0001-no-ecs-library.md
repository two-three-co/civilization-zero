# ADR-0001: ECS ライブラリを採用せず、正準順序の Vec + SoA を使う

- 状態: 採用 (2026-10-17)

## 文脈
Phase 1 の要件は 1,000〜100,000 体、コンポーネント種は数個、決定論的再現が最優先。

## 検討した選択肢
| 案 | 長所 | 短所 |
|---|---|---|
| bevy_ecs | 成熟、並列スケジューラ | システム実行順・アーキタイプ走査順が暗黙的で、決定論の保証を自前で積む必要がある。依存が大きく、Bevy のリリース周期で破壊的変更が多い |
| hecs / legion 等 | 軽量 | エンティティ ID の再利用・走査順が実装依存。legion は保守停滞 |
| **Vec<Agent>（id 昇順）+ グリッドは SoA** | 走査順が仕様として明確、serde で丸ごと保存、ハッシュが容易、依存ゼロ | コンポーネントが増えると構造体が肥大化 |

## 決定
第3案。エージェントは id 昇順の `Vec<Agent>`、資源グリッドは `Vec<u32>` の SoA。

## 結果・再検討条件
- 計測: 10 万体で serial 2.26 ms/tick（docs/STATUS.md）。現時点で性能上の理由で ECS は不要。
- Phase 3〜4 で可変なコンポーネント集合（契約・所属組織など）が増え、AoS がキャッシュ効率上の問題になったと**計測で**示された時点で、agent 側を SoA 化するか ECS を再評価する。
