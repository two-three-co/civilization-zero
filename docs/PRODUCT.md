## 1. 製品ゴール

**Claude Code で大規模開発を回し、最終的に一般ユーザーが遊べる製品にする。**

研究としての正しさ（決定論・再現性・検証可能性）は引き続き守るが、それ自体が目的ではなく、遊べる製品の土台として守る。
ゲームの中核体験「観察する → 巻き戻す → 介入する → 分岐を並べて比較する → なぜ違いが生まれたかを辿る」は、
カーネルが bit 単位で再現可能であり、初期状態・シード・介入ログから任意の時点を復元できることで初めて成立する。
したがって研究用の要件（ADR-0002〜0004, 0008, 0012）は製品要件として引き続き守る。

## 2. 製品の理念

作りたいものは、次の 3 つを満たすもの。

- まだ誰も見たことのないもの
- 公開後にどうなるか予想がつかないもの
- 人間が介入し、問い、確かめることで、人間にとって意味のあるものになり、人間の社会や歴史についての理解を広げる・深めるもの

見たことがないだけのノイズでも、既存のものの再現でもなく、
**「最初は知らなかったが、確かめると腑に落ちる」現象を人間に届ける**ことを目指す。
人間は観客ではなく、現象に問いを立て、介入し、名前をつけて理解に変える役割を担う。

## 3. まだ決めないこと

ゲームの具体的な遊び方（観察型・パズル型・箱庭型・プレイヤー同士がつながる型など）は、
最初の遊べるマイルストーン「Toy 1」が完成してから、製品オーナーが触って決める。
それまでは特定の遊び方に設計を固定しない。

## 4. Toy 1（最初の遊べるマイルストーン）

ブラウザで次の一連の操作ができること。

| # | 操作 | 状態（2026-10-18） |
|---|---|---|
| 1 | 文明が発展する様子を観察する | 済（Phase 2、公開 URL） |
| 2 | 任意の時点に巻き戻す | 済（Phase 2） |
| 3 | 介入する（干ばつ・資源量の変更など） | 済（Phase 2〜4: 干ばつ、資源量、個体の追加 / 除去、方策の切替、規則の布告 / 廃止 / 憲章） |
| 4 | 分岐した世界と元の世界を並べて比較する | 済（Phase 2〜4: 2 世界同期、比較表、曲線、Verify） |
| 5 | **「なぜ違いが生まれたか」を辿れる** | **未**。分岐の差分は数値で見えるが、介入 → 最初に決定が変わった個体 → 連鎖、という因果の経路を画面で辿る手段はまだない（設計原則 C） |

Toy 1 の完了判定は、製品オーナーがブラウザで 5 操作を自力で体験できることで行う（コードは読まない。設計原則 F）。
Phase 2 の完了判定（ADR-0010）は旧定義の 1〜4 に対するものであり、新定義では 5 が残っている。

## 5. 設計原則

### A. 実行環境を固定しない

`simulation-core` はネイティブと WASM（ブラウザ）の両方で動く構成を維持する。
「ブラウザだけで完結する設計」にも「サーバー必須の設計」にも固定しない。
現在の配信は静的ファイルだけ（サーバーなし）だが、それは現時点の選択であって前提ではない。

### B. 歴史を共有可能な単位にする

歴史は「初期状態 + シード + 介入ログ」から完全に再現できる形を保つ。
これを、将来プレイヤー間で共有・引き継ぎできる単位として扱えるようにしておく。
複数プレイヤーが同じ世界や同じ歴史ツリーに介入する可能性は ADR に検討事項として記録する（今は実装しない）。

### C. 「なぜ」を辿れる記録

イベント台帳には「何が起きたか」だけでなく、その原因となった行動・状態を辿れる情報を残す。
人間が後から「なぜこうなったか」を説明・検証できることが、この製品の価値の中心である。

### D. 事実と解釈を分ける

世界の事実はプログラムが決める。LLM を使う場合は説明・語りに限定し、状態遷移には一切関与させない。
説明文を生成する場合は「記録された事実」と「解釈」を明確に区別できるデータ構造にする。

### E. 人間社会の用語でラベルを付けない

現象に「所有権」「封建制」「通貨」などのラベルを自動で付ける処理をシステム側に入れない。
人間の既存概念に翻訳した瞬間に、新しい現象が既知のものに変わってしまうため。
研究用の観測指標として内部で判定するのは構わないが、プレイヤー向けの表示では命名を人間側の役割として残す。

### F. デモで確認できる完了条件

今後の各フェーズの完了条件には、製品オーナーがブラウザで見て確認できるデモを必ず含める。
製品オーナーはコードを読まずに、実際に触って判断する。

### 従来の原則との対応

改定前の原則 1〜4 は A〜F に吸収される: 1（世界の事実はプログラムが決める）と 2（LLM は語りに限定）は D、
3（デモで完了判定）は F、4（研究の主張と演出を混同しない）は D と E。
研究側の規則（「創発」「世界初」を証拠なしに書かない。docs/research/HYPOTHESES.md）はそのまま残る。

## 技術方針（製品観点）

- `simulation-core` と `multiverse` はネイティブと `wasm32-unknown-unknown` の両方でビルドし、CI が wasm = native のゴールデン一致を照合する（原則 A）。
- 現在の UI はブラウザ内実行（React + Vite + Canvas、Web Worker 1 つ = 世界 1 つ、静的配信）。サーバーは「共有・保存」が必要になったときに検討する（ADR-0009）。
- 性能目標: 1,000〜2,000 体の世界を、ブラウザ内で実時間 60 tick/s 以上で進められること。計測で確認する。
- 歴史の単位は `WorldConfig`（シードを含む）+ 介入ログ（`EventLog` の `Intervened`）。再生は再実行で、台帳の出生・死亡・相互作用と照合する（ADR-0012）。

## 今やらないこと

- ゲームの遊び方の固定（3.）。
- マルチプレイ、アカウント、課金（B の検討事項として ADR に残すだけ）。
- LLM による NPC の意思決定、制度判定、状態遷移への関与。
- 現象への自動ラベル付け（E）。
- 3D 表示。
